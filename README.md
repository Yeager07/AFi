# AFi — Accounting of Finances

Мобильное приложение для учёта и анализа доходов и расходов малого 
бизнеса. Разработано как учебный проект в рамках курса «Визуальное 
программирование» с применением методологии работы с генеративными 
моделями («Золотые правила»).

**Платформа:** Android (приоритет), iOS и Windows — в перспективе  
**Стек:** .NET 10 + .NET MAUI + C# 12, Python 3.11 (OCR-сервис)  
**Хранение:** SQLite, полностью локально  
**Автор:** Есипенко Игорь Ярославович

## О проекте

### Предыстория

У моего друга — небольшая кофейня. Он сам закупает зерно, платит 
за аренду, налоги и зарплату бариста, но постоянно путается в цифрах: 
сколько ушло на закупки в прошлом месяце, сколько стоила аренда, 
сколько нужно отложить на следующий месяц. Готовые решения (типа 
«Мой Склад», «Дримкас») либо слишком дорогие, либо перегружены 
функциями, которые микробизнесу не нужны.

### Цель

Простое приложение, которое:

- Позволяет за 5 секунд внести трату или доход.
- Показывает, куда уходят деньги, без сложных отчётов.
- Предупреждает о регулярных платежах и подсказывает ожидаемые 
  расходы на следующий месяц.

### Ключевые возможности

- **Учёт операций** — быстрый ввод доходов и расходов с категоризацией.
- **Позиции чека** — разбивка одной операции на конкретные товары 
  с ценой и количеством (например, «Молоко 3 шт × 90 ₽»).
- **Фото чека** — прикрепление фотографии к операции и полноэкранный 
  просмотр с пинч-зумом.
- **Распознавание чека (OCR)** — четыре способа получить позиции 
  из фото: автоматический QR-скан, ручное выделение QR, ручной 
  ввод реквизитов и **собственный OCR-пайплайн** (PaddleOCR + 
  постобработка).
- **Визуализация** — круговая диаграмма расходов по категориям 
  и столбчатая динамика за 6 месяцев.
- **Drill-down** — топ позиций внутри каждой категории.
- **История** — детальный просмотр операций с фильтрами по периоду 
  и категории.
- **Напоминания** — уведомления о регулярных платежах за N дней 
  до даты.
- **Прогноз бюджета** — предсказание расходов на следующий месяц 
  гибридным алгоритмом.
- **5 тем оформления** — Светлая, Тёмная, Космос, Хеллоуин, Аркадная.
- **Мультивыбор** — массовое удаление операций и напоминаний.
- **Экспорт/импорт БД** — через Share и FilePicker (DataBackupService).

## Требования

### Функциональные

#### 1. Ввод и категоризация операций

- Добавление дохода или расхода: сумма, категория, дата, комментарий.
- **Категории по умолчанию (расходы):** Аренда, Закупки (сырьё), 
  Налоги, Коммунальные услуги, АЗС, Транспорт, Кафе и рестораны, 
  Дом и ремонт, Одежда и обувь, Подписки, Цветы, Прочее.
- **Категории по умолчанию (доходы):** Выручка, Зарплата, 
  Прочие поступления.
- Каждая категория имеет **иконку-эмодзи** для визуального распознавания.
- Пользователь может **добавлять и удалять** свои категории 
  (стандартные — защищены от удаления).
- **Редактирование операций:** разрешено менять категорию, дату, 
  комментарий. **Сумма неизменяема** — принцип immutable amount 
  из бухгалтерского учёта.
- **Позиции чека** — разбивка операции на товары с количеством 
  и ценой. Если позиции есть, сумма операции = сумма позиций.
- **Фото чека** — прикрепление из галереи или через камеру.

#### 2. Получение позиций из фото чека

Четыре независимых способа, в порядке приоритета для пользователя:

1. **Автоматический QR-скан.** С фото чека через ML Kit (BarcodeScanning.Native.Maui) 
   декодируется фискальный QR, затем реквизиты отправляются в API 
   `proverkacheka.com`. Точность 100 %, но есть лимит запросов.
2. **Ручное выделение QR.** Если автоматика не видит QR — пользователь 
   выделяет область вручную (QrCropPage с GraphicsView), после чего 
   QR декодируется с нарезкой на плитки.
3. **Ручной ввод реквизитов.** ФН / ФД / ФП / дата / сумма — 
   собирается `qrraw`-строка и отправляется в тот же API.
4. **Собственный OCR-пайплайн.** Отправка фото на локальный 
   Python-сервис (PaddleOCR + парсер), который возвращает 
   структурированный список `[{name, quantity, price}]`. 
   Не зависит от внешних API, работает на своём железе.

#### 3. Визуализация статистики

- **Круговая диаграмма** — расходы по категориям за период.
- **Столбчатая диаграмма** — доходы и расходы за последние 6 месяцев.
- **Итоговые карточки** за период: Доход, Расход, Баланс.
- **Drill-down:** тап по «Топ позиций по расходам» внутри категории 
  показывает 5 самых крупных позиций.
- **Связка со страницей «История»:** тап по категории в легенде 
  открывает Историю с применённым фильтром по этой категории и периоду.

#### 4. Баланс и регулярные платежи

- **Баланс.** Пользователь вводит начальный баланс один раз. Приложение 
  показывает текущий: `начальный + доходы − расходы`.
- **Регулярные платежи** — напоминания, а не автоплатежи:
  - Название, сумма, день месяца.
  - Настройка «за сколько дней напоминать» (0–30).
  - Настройка времени напоминания.
  - Переключатель вкл/выкл для каждого платежа.
  - Локальные уведомления через `ExactAllowWhileIdle` (работает 
    даже в Doze-режиме).
- **Банковские карты не хранятся.** Приложение — учётный инструмент.

#### 5. Прогноз бюджета на следующий месяц

Гибридный алгоритм — **частотный фильтр + медиана**:

1. Берём 3 последних **полных** месяца.
2. Для каждой категории считаем, в скольких месяцах она встречалась.
3. **3 месяца** → медиана значений (устойчиво к выбросам).  
   **2 месяца** → среднее.  
   **1 месяц** → не включаем (разовые крупные траты).
4. Сумма «зачётных» категорий = прогноз.

**Пример:** если «Закупки» имели суммы 10 000, 12 000 и 80 000 ₽ 
(в одном месяце купили оборудование), среднее = 34 000 ₽ (завышено), 
медиана = 12 000 ₽ (реалистично).

### Нефункциональные

- **Локальное хранение** — все данные в SQLite, без сервера.
- **Работа офлайн** — приложение не требует интернета (кроме QR-сценариев 
  и OCR через локальный сервис).
- **Кроссплатформенность** — Android, iOS, Windows из одного кода.
- **Простой UI** — минимум экранов, ≤2 нажатия до любой функции.

Приложение состоит из 7 основных экранов:

### Главная — рабочая панель

- Карточка текущего баланса.
- Форма ввода операции: сумма, тип, категория, дата, комментарий.

- Фото чека (опционально) + четыре кнопки получения позиций:

- Пагинация по 10 операций с кнопкой «Показать ещё».

### История — детальный просмотр

- Фильтр по периоду: 10 пресетов (Сегодня, Вчера, …, Свой период).
- Фильтр по категории.
- Итоговые карточки за период.
- Полный список с пагинацией по 100.
- Редактирование операций через модалку `TransactionEditPage`.

### Статистика — визуализация

- Переключатель «Круговая / Динамика».
- Круговая диаграмма расходов по категориям с легендой.
- Столбчатые диаграммы за 6 месяцев.
- Drill-down по категориям (топ-5 позиций).

### Напоминания — регулярные платежи

- Список напоминаний с переключателем вкл/выкл.
- Форма создания/редактирования: название, сумма, тип, категория, 
  день месяца, «за сколько дней», время, комментарий.

### Прогноз — предсказание расходов

- Расчёт по гибридному алгоритму.
- Таблица: категория → значение → включена в прогноз (да/нет).
- Итоговая сумма прогноза.

### Категории — управление

- Две вкладки: Расходы и Доходы.
- Список с иконками.
- Добавление и удаление пользовательских категорий.

### Настройки

- Выбор темы (сетка 2×3 с превью 5 тем).
- Начальный баланс.
- Экспорт/импорт БД.

## Архитектура OCR-пайплайна

Из-за того что PaddleOCR — Python-библиотека, а MAUI — C#-приложение, 
реализована схема «локальный микросервис»:

Android-приложение (C#)
↓ HTTP Multipart (фото чека, Content-Type: image/jpeg)
Python-сервис (FastAPI + PaddleOCR, GPU)
↓ JSON: {items: [{name, quantity, price}], total}
Android-приложение заполняет форму операции

**Компоненты:**

| Компонент | Роль |
|---|---|
| `ocr/app.py` (FastAPI) | Принимает фото, разворачивает по EXIF, даунскейлит до 2500 px, прогоняет через PaddleOCR |
| `ocr/extract_items.py` | Группирует блоки по координатам Y в строки, извлекает позиции, применяет OCR-фиксы и адаптивный fuzzy-словарь |
| `Services/OcrService.cs` | C#-обёртка для HTTP-вызова Python-сервиса |
| `TransactionEditViewModel` / `MainViewModel` | Команда `RecognizeReceiptWithOcrCommand`, заполняющая `CurrentItems` |
| `Controls/TransactionFormView.xaml` | Кнопка «🔍 Распознать (OCR)» рядом с кнопкой «Ввести реквизиты чека» |

**Этапы обработки:**

1. Пользователь добавляет фото чека и нажимает «Распознать (OCR)».
2. `OcrService` отправляет файл `POST-запросом` на `http://<IP>:8000/api/ocr`.
3. Python-сервис:
   - **разворачивает по EXIF** (`ImageOps.exif_transpose`) — критично, 
     потому что камера телефона часто пишет `Orientation: 6`, а 
     PaddleOCR читает пиксели «как есть»;
   - **даунскейлит** до 2500 px по длинной стороне (стабильная детекция);
   - сохраняет во временный PNG (без потерь);
   - передаёт путь в `PaddleOCR.predict()`.
4. PaddleOCR возвращает список `{text, confidence, bbox}`.
5. Парсер (`extract_items.py`):
   - фильтрует мусор (confidence < 0.6, решётки QR, пустые строки);
   - **группирует блоки по Y** (порог 15 px) — восстанавливает строки;
   - внутри строки сортирует по X;
   - активирует «зону товаров» после «НАИМЕНОВАНИЕ» и деактивирует 
     после «ИТОГ»/«ОПЛАТА»;
   - regex-ом извлекает количество (`1.000ШТ`, `2.00ОШТ.X`), 
     цены (`179.99`), НДС (`НДС22%`, `НДC10%`, `HAC10%`);
   - применяет **OCR-фиксы** (`НОГУРТ→ЙОГУРТ`, `ХАХАР→САХАР`) 
     и **адаптивный fuzzy-словарь** (порог 0.80 для коротких, 
     0.85 для длинных слов);
   - защищает реальные бренды (`ЧЕБУПИЦЦА`, `ПРОВАНСАЛЬ`) 
     от ошибочных «исправлений».
6. C#-клиент получает JSON, создаёт `TransactionItem` и заполняет форму.
7. Сумма позиций автоматически пересчитывается и сверяется 
   с суммой операции.

**Результат на реальном чеке «Монетка»:**
- 124 текстовых блока → 40 строк → 10 позиций.
- Сумма 1424.89 ₽ — **сходится с ИТОГОМ чека до копейки**.
- Время распознавания: 3–10 секунд на RTX 3050.
- 1–2 OCR-ошибки в названиях на чек исправляются fuzzy-словарём.

**Почему LayoutLMv3 не понадобился:** табличная структура чеков 
российских сетей настолько регулярна, что группировки по координатам 
Y + сортировки по X достаточно. LayoutLMv3 остаётся в резерве — для 
нестандартных вёрсток (многострочные названия, сложные раскладки).

## Как запустить

### Требования

- **.NET 10 SDK** — [скачать](https://dotnet.microsoft.com/download/dotnet/10.0)
- **MAUI workload** — `dotnet workload install maui`
- **Android SDK** — устанавливается автоматически через workload
- **Физическое устройство** (Android) с включённой USB-отладкой 
  или эмулятор
- **Python 3.11** — только для OCR-сервиса
- **GPU NVIDIA** с CUDA 11.8 (опционально — для ускорения OCR; 
  на CPU тоже работает, но медленнее)

Текущий этап и планы
Что работает сейчас
Приложение: учёт операций, категории, визуализация, напоминания,
прогноз, позиции чека, фото, экспорт/импорт БД.

Четыре способа получить позиции чека: QR-скан, ручное выделение QR,
ручной ввод реквизитов, собственный OCR.

OCR работает через локальный сервис на ноутбуке (Python + PaddleOCR +
FastAPI). Телефон обращается по Wi-Fi.

Известные ограничения OCR
Зависимость от ноутбука и сети. OCR работает только когда запущен
Python-сервис, и телефон в той же Wi-Fi сети.

OCR-ошибки в названиях (1–2 на чек) — исправляются fuzzy-словарём
и ручной правкой пользователя.

EXIF-поворот обрабатывается на сервере, но требует внимания при
добавлении новых форматов.

Что в работе
Сбор датасета чеков — 50–100 штук из 5–10 разных магазинов
(не только продуктовых: кофейни, аптеки, АЗС, строймагазины).

Ручная разметка пар «кроп строки → правильный текст».

Ближайшие планы
Fine-tune recognition-модели PaddleOCR на размеченных кропах.
Это устранит OCR-фиксы и fuzzy-словарь — модель будет читать
ЙОГУРТ корректно на уровне нейросети.

Перенос модели в ONNX Runtime на Android — полный офлайн-инференс
без ноутбука и сети. Кандидаты: RapidOCRSharpOnnx, LMSupply.Ocr.

Портирование парсера на C# — вместе с переносом ONNX, чтобы
весь пайплайн работал в MAUI-приложении.

Введение LayoutLMv3 — если в датасете появятся чеки со сложной
структурой (многострочные названия, нестандартные вёрстки).
