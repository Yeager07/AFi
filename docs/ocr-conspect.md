# 📄 Итоговый конспект по OCR и Document AI (теория)
Проект: AFi — распознавание чеков
Назначение: отчёт по учебному заданию (визуальное программирование) + навигатор для дальнейшей разработки
Формат: только теория, без кода

---

## 1. Введение: задача и контекст

**Проблема.** Для проекта AFi нужно из фотографии чека получать структурированные данные о товарах: название, количество, цена. Распознать текст — только полдела: после OCR мы получаем «плоский» список строк, и компьютер не знает, что «Молоко» — это товар, а «104.99» — его цена.

**Почему не Regex.** Regex видит только текст, но не layout: не знает, в какой колонке стоит число, на какой строке, рядом с каким словом. На реальных чеках вёрстка нестабильна (у каждого магазина свой порядок полей и разделители), числа повсюду (артикулы, ИНН, даты, номера касс), OCR разбивает числа и слова («104.99» → «104. 99»). Правила под каждый магазин нужно писать заново — Regex не обобщается.

**Бизнес-цель.** Фото чека → JSON вида `[{name, quantity, price}, ...]` → маппинг в поля формы операции AFi.

## 2. Основы CV

**Изображение для нейросети — тензор чисел.** Grayscale — `H×W×1`, RGB — `H×W×3`, значения нормализуются к `[0,1]` или `[-1,1]`. Разрешение критично для OCR: при уменьшении мелкий текст «сливается». Реальные фото чеков — вариации тензора: тени, блики, изгибы, перспектива, низкий контраст.

**CNN** решает проблему полносвязных сетей через локальность (маленькие окна) и разделение весов (одно ядро скользит по всей картинке). Свёртка — скользящее ядро, в каждой позиции считает скалярное произведение с кусочком изображения; результат — **карта признаков (feature map)**, где значение ячейки показывает, насколько сильно сработал узор. **Pooling** (обычно max 2×2) уменьшает размерность и даёт устойчивость к небольшим сдвигам. С глубиной признаки абстрагируются: края → штрихи → части букв → строки и структуры.

**Feature map — не ответ, а промежуточное представление.** Предсказание получается через «голову» модели, и она зависит от задачи: классификация — global pooling + FC + softmax; детекция — поканальные предсказания + постобработка в bbox; распознавание — последовательность признаков + декодер (CTC/attention) → строка.

**Эволюция архитектур.** LeNet (1998) — маленькая CNN для цифр; AlexNet (2012) — глубина + ReLU + dropout + GPU, запустила революцию; VGG (2014) — глубина и однородность (3×3), но тяжёлая; ResNet (2015) — **skip connections** (`output = F(x) + x`), решают затухание градиента и позволяют обучать сети на 50–152 слоя. ResNet-50/101 — стандартный backbone в OCR и Document AI.

**Transfer learning.** Pretrained-модели (ImageNet) уже выучили базовые признаки (края, текстуры, формы). Два режима: feature extraction (backbone заморожен, обучаем голову — быстро, мало данных) и fine-tuning (размораживаем часть слоёв, маленький LR — точнее, но требует больше данных). Для AFi: PaddleOCR — «из коробки», LayoutLM — fine-tune на 100–300 чеках; обучение с нуля нереалистично.

**Аугментации** расширяют разнообразие данных: геометрические (поворот, сдвиг, перспектива, crop), фотометрические (яркость, контраст, шум, размытие), специфические для документов (тени, блики, изгиб, «выцветание» термопечати). Правило: имитировать реальные вариации прода, а не «что попало» — отражение текста и сильное размытие вредят.

## 3. Как работает OCR

**OCR — это две отдельные задачи.** **Text Detection** — «где на картинке текст» (bbox, регрессия координат). **Text Recognition** — «что написано в области» (sequence-to-sequence). Их разделяют, потому что у них разные данные, разметка и архитектуры; разделение упрощает обучение, отладку и независимое улучшение. End-to-end (Donut) возможен, но требует много данных.

**Классический OCR (Tesseract).** Пайплайн: предобработка → сегментация на строки/слова/символы → распознавание по шаблонам/признакам → языковая модель. Корневая уязвимость — **зависимость от посимвольной сегментации**: на слипшемся, зашумлённом, искривлённом тексте она ломается, а языковая модель «исправляет» артикулы и коды в несуществующие слова. Отсюда CER 20–50% на реальных чеках. Tesseract 4 добавил LSTM-режим, но детекция осталась классической.

**Нейросетевой OCR — два подхода к распознаванию:**

| Критерий | CTC | Attention |
|---|---|---|
| Механика | предсказывает символ для каждого «столбца», декодирует схлопыванием повторов и blank | энкодер-декодер, генерирует символы по одному с «подглядыванием» в картинку и в сгенерированное |
| Контекст | слабый | сильный |
| Скорость | быстрее (параллельно) | медленнее (авторегрессия) |
| Данные | меньше | больше |
| Галлюцинации | редко | возможны |
| Применение | CRNN, Tesseract 4 | TrOCR, Donut |

**Детекция текста.** **EAST** — один проход CNN, быстрый, хуже на плотном/искривлённом тексте. **DBNet** — обучаемая (дифференцируемая) бинаризация, стандарт для документов, основа PaddleOCR. **CRAFT** — регионы символов + affinity, хорош для сцен. Общая схема: backbone → FPN → голова (вероятность текста + смещения до границ) → threshold → bbox → NMS.

**Распознавание текста.** **CRNN (CNN + RNN + CTC)** — классика: CNN-признаки → BiLSTM для контекста → CTC-декодирование; не требует посимвольной разметки, устойчив к слипшемуся тексту. **TrOCR** — ViT-энкодер + трансформерный декодер с attention; точнее на контексте, но тяжелее и требует больше данных.

**PaddleOCR** — практический стандарт «из коробки»: пайплайн **DBNet + CRNN+CTC** с мультиязычными pretrained-весами (включая кириллицу), обучен на реальных «диких» изображениях. Выдаёт список `{bbox, text, confidence}` — ровно то, что нужно следующему этапу. На чеках справляется лучше Tesseract, потому что не требует посимвольной сегментации и не «исправляет» не-слова.

**Метрики.** **CER** (Character Error Rate) = (S + D + I) / N через расстояние Левенштейна: <5% — отлично, <15% — приемлемо, >30% — плохо. **WER** — то же на уровне слов. Для AFi важнее обеих — **F1 по полям** (об этом в разделе 5).

## 4. Понимание структуры документа

**Задача Information Extraction.** Для каждого фрагмента текста определить поле: NAME / PRICE / QUANTITY / TOTAL / DATE / STORE / OTHER. После OCR мы имеем только строки — модель должна понять, что «Молоко 3.2%» — это NAME, «2» — QUANTITY, «104.99» — PRICE, а «ИТОГО: 255.48» — TOTAL, а не ещё один товар.

**Layout Understanding — ключевая идея.** Положение слова на странице несёт огромную информацию, часто важнее самого слова. Слова в одной вертикальной колонке — одно поле; слова на одной горизонтальной линии — одна позиция (товар + кол-во + цена + сумма).

**Bounding box (bbox)** — прямоугольник вокруг слова `[x_min, y_min, x_max, y_max]`. В OCR-пайплайне задаёт область для распознавания; **в LayoutLM его роль другая** — координаты кодируются в **2D-position embedding** и добавляются к токену, чтобы модель учитывала пространственное положение: привязку к колонкам и строкам, относительное положение и размер. Это позволяет различать «104.99» в колонке цен (PRICE) и в служебной строке (OTHER).

**Ключевые модели:**
- **LayoutLM v1 (2020)** — текст + изображение + layout; 2D-position embedding от bbox; pretrained на миллионах документов.
- **LayoutLMv2 (2021)** — визуальный backbone внутри модели, spatial-aware attention, multi-task pretraining.
- **LayoutLMv3 (2022)** — единая архитектура (ViT-патчи + текст в одном трансформере), unified masking, лучшие результаты на FUNSD/CORD/SROIE; **де-факто стандарт**.
- **Donut (2022)** — OCR-free, end-to-end «фото → JSON» (Swin-энкодер + BART-декодер). Плюсы: один компонент, нет накопления ошибок OCR. Минусы: требует много данных, тяжёлый, сложнее отлаживать, может галлюцинировать, плохо на мелком тексте.
- **PICK (2020)** — извлечение пар «ключ-значение» через граф документа; хорош для форм, менее универсален для чеков.

**NER в документах** — классификация токенов по полям в **BIO-разметке** (`B-NAME`, `I-NAME`, `O`); постобработка собирает токены в поля. В отличие от Regex, модель учится на примерах, учитывает контекст и координаты, обобщается на новые вёрстки.

**Датасеты:** **SROIE** (~1000 чеков, 4 поля: company/date/address/total — базовая классика, но без товаров), **CORD** (~1000 индонезийских чеков с товарами и их полями — ближе к AFi), **FUNSD** (~200 форм, key-value), **WildReceipt** («дикие» чеки). Готовых «русских чеков с товарами» мало — SROIE/CORD для проверки подхода, для production нужны свои 100–300 чеков.

## 5. Выбор пайплайна для AFi (главный вывод)

**Три подхода:**

| Критерий | OCR + Regex | OCR + LayoutLM | Donut |
|---|---|---|---|
| Данные | не нужны | 100–300 чеков | тысячи |
| Layout | нет | да (bbox) | неявно |
| Обобщение | плохое | хорошее | хорошее при данных |
| Отладка | высокая | высокая (по компонентам) | низкая |
| Ресурсы | низкие | средние | высокие |
| Галлюцинации | нет | низкий риск | высокий |
| Мелкий текст | зависит от OCR | зависит от OCR | плохо |
| **Для AFi** | вспомогательно | **рекомендуется** | позже, при данных |

**Аргументация отказа:**
- **Regex** не видит layout, не обобщается, ломается на повсеместных числах и OCR-шуме. Годится только как вспомогательная постобработка (нормализация «104,99» → «104.99»).
- **Donut** требует много данных, тяжёлый, сложно отлаживать, галлюцинирует, плохо на мелком тексте, и как OCR-free он «пропускает» изучение OCR-моделей — для учебной цели это минус.

**Наш выбор: PaddleOCR + LayoutLMv3 + постобработка.**

**Текстовая схема пайплайна:**

Фото чека
→ предобработка (resize, deskew, контраст — по необходимости)
→ PaddleOCR (DBNet + CRNN+CTC): {text, bbox, confidence}
→ LayoutLMv3 (token classification, BIO): NAME / PRICE / QUANTITY / TOTAL / OTHER
→ постобработка: сборка токенов в позиции по строкам/колонкам (bbox)
→ JSON: [{name, quantity, price}, ...]
→ маппинг в поля формы операции AFi

**Почему именно так:** учитывает layout, обобщается на новые вёрстки, прозрачен для отладки по компонентам (видно, где ошибка — в OCR или в LayoutLM), реалистичные требования к данным (50–100 чеков — старт, 200–300 — комфортно), есть готовые веса в HuggingFace и «из коробки» PaddleOCR, соответствует учебной цели — разобраться именно в OCR-моделях.

**Метрики оценки:** CER/WER для OCR-этапа, **F1 по полям** для извлечения (главная метрика AFi), end-to-end accuracy (доля чеков, где все поля верны).

## 6. Юридические и технические ограничения

**API ФНС не подходит для коммерции.** Предназначен для проверки подлинности чеков гражданами, а не для массового извлечения данных; условия запрещают коммерческое использование и монетизацию; массовые запросы — нарушение условий и потенциально законодательства. Данные чеков могут содержать персональные сведения (152-ФЗ) — в коммерческом продукте нужны согласия и защита. **Вывод:** строим собственный пайплайн, работающий локально/на нашем сервере.

**Технические ограничения:**
- Свой OCR требует данных: 50–100 размеченных чеков для старта fine-tune LayoutLM (лучше 200–300); для recognition — кропы строк с транскрипциями.
- BIO-разметка трудозатратна — можно начать с 30–50 чеков и дообучать.
- Реальные фото требуют предобработки и аугментаций.
- Русский язык: PaddleOCR поддерживает кириллицу, но проверять надо; LayoutLM мультиязычный, но fine-tune на русских чеках обязателен.
- Конфиденциальность: чеки содержат персональные данные — обработка должна быть защищена.

## Короткое резюме (одним абзацем, для защиты)

> Для распознавания чеков в AFi выбран пайплайн **PaddleOCR + LayoutLMv3 + постобработка**. PaddleOCR (DBNet + CRNN+CTC) решает детекцию и распознавание текста, устойчив к теням, изгибам и слипшемуся тексту, поддерживает кириллицу. LayoutLMv3 через 2D-position embedding от bbox учитывает layout и классифицирует токены по полям (NAME/PRICE/QUANTITY/TOTAL/OTHER); постобработка собирает токены в позиции и формирует JSON для формы операции. Такой выбор обоснован: учитывает layout (в отличие от Regex), обобщается на новые вёрстки, прозрачен для отладки по компонентам, реалистичен по данным (50–300 чеков) и соответствует учебной цели — разобраться в OCR-моделях. Donut отклонён из-за требований к данным и сложности отладки, Regex — из-за отсутствия обобщения и нечувствительности к layout. API ФНС не используется по юридическим причинам.
